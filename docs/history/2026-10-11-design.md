# code-review-ai v1 — design

Autonomous code review and audit agent, deployable per company, that takes work over agent-link
and from its own GitHub polling, reviews pull requests, local working trees and whole codebases,
and composes every reviewer's instructions from a prompt template that includes guideline
files from four roots: this framework, a company repo, a project within that company, and the
reviewed repository itself.

Status: approved design, 2026-10-11. Predecessor: the PR Review Harness at `../code-review`
(bash + systemd + bubblewrap, one reviewer agent per repo, human-gated posting).

## 1. Purpose

The previous harness proved the review policy (severity rubric, fix-now-vs-defer triage,
re-review discipline) and the reviewer/poster split, but welded guidelines to specific repos,
ran only on a scheduler, could not take requests from other agents, and ran reviewers in a
sandbox so tight they often could not verify their own findings.

v1 replaces it with a **framework** that any company deploys for itself. The framework holds
general prompts, guidelines and templates only. Everything company- or project-specific lives
in a **company repo** that a deployment references by URL or path.

## 2. Decisions (agreed)

| # | Decision |
|---|---|
| D1 | Work arrives over **agent-link** and from the deployment's **own GitHub polling**. Both produce the same internal request. |
| D2 | A request for several review types runs **one specialist agent per type**, in parallel, then a **merger** produces one review. |
| D3 | The runtime is **Claude Code itself**: a long-lived window is the coordinator and agent-link peer; specialists and the merger are Claude Code subagents. No new agent runtime. |
| D4 | Results go to a file and back over agent-link; for GitHub PRs the deployment **posts autonomously** with the old approve / request-changes rules. |
| D5 | Guidelines come from four roots (framework, company repo, project, reviewed repo); a **prompt template** with explicit include lines, expanded by a **deterministic resolver**, yields one prompt file per specialist. No model in the loop. (Amended from the original layered-override model; see §5.1.) |
| D11 | The framework ships **nine review types** (the original seven run by default; `spec-compliance` and `performance` are opt-in), **six kinds** (`service`, `library`, `tool`, `website`, `contracts`, `spec`), opt-in **guideline packs** under `guidelines/packs/<pack>/<type>.md` and several ready templates under `prompts/`. Content is distilled from the previous review agents, the SDD framework playbooks and reviewer personas, superpowers' reviewer prompts, the enforcing-code-quality skill and a survey of public agent frameworks; nothing company-specific enters the framework (2026-10-12). |
| D6 | v1 covers **PR reviews, codebase audits and local working-tree reviews**. |
| D7 | A deployment is a **Docker Compose project**. Containment is the container, an egress allowlist and a narrowly scoped GitHub identity, not Claude permission allowlists. |
| D8 | Each deployment acts as a **dedicated bot GitHub account** with a fine-grained PAT. |
| D9 | Claude Code inside the container uses a **subscription login persisted in a volume**. |
| D10 | The framework repo holds **no company or project data**. The company repo is a reference in the deployment config. |

## 3. Architecture

```
                   host machine (one per developer / CI box)
 ┌────────────────────────────────────────────────────────────────────────┐
 │  agent-linkd hub ◄──── coding agents, human relay, other peers         │
 │        ▲  (bridge address)                                             │
 │        │                                                               │
 │  ┌─────┴──────────── docker compose: code-review-<company> ─────────┐ │
 │  │  reviewer container (non-root, egress allowlist)                  │ │
 │  │                                                                   │ │
 │  │  tmux ─► claude (coordinator window, channels flag, perms off)    │ │
 │  │            │  cron: discover PRs ──► runs/<id>/request.json       │ │
 │  │            │  agent-link channel ─► runs/<id>/request.json        │ │
 │  │            │                                                      │ │
 │  │            ├─ prep-target   (worktree | checkout | snapshot)       │ │
 │  │            ├─ resolve-run        ──► runs/<id>/plan.json          │ │
 │  │            ├─ prep-target siblings (clones from plan.json)        │ │
 │  │            ├─ compose-prompt ×N  ──► runs/<id>/prompts/<type>.md  │ │
 │  │            ├─ Agent(specialist) ×N ─► runs/<id>/findings/<type>.md│ │
 │  │            ├─ Agent(merger)        ─► runs/<id>/review.md         │ │
 │  │            └─ deliver: agent-link reply · post-review (gh)        │ │
 │  │                                                                   │ │
 │  │  mounts: deployment dir (bind, cwd) · claude home (volume)        │ │
 │  │          local_roots (bind, read-only, same paths as host)        │ │
 │  └───────────────────────────────────────────────────────────────────┘ │
 └────────────────────────────────────────────────────────────────────────┘
```

Three agent roles, all Claude Code:

- **Coordinator** — the interactive window. Owns intake, run state, prompt composition,
  dispatch, delivery and all agent-link conversation. Its `CLAUDE.md` is generated at deployment
  time from `agents/coordinator.md` plus the company overlay.
- **Specialist** — a subagent (`.claude/agents/specialist.md`) whose system prompt says only:
  read the prompt file you were given before anything else, follow it, write your findings to
  the path it names. Identity, guidelines and task context all come from the composed file. One
  generic definition serves every review type.
- **Merger** — a subagent that reads all `findings/*.md` for a run, dedupes findings that
  several specialists raised, orders by severity and writes `review.md`, which keeps a merged
  machine-readable findings block (§9.2). It never adds findings. When specialists disagree
  about a duplicated finding, the merged entry keeps the highest severity, the most cautious
  fix risk, and names every source; the recommendation is then re-derived from the triage
  table in the common guidelines, never invented. The verdict line it writes is informational;
  the verdict that is posted is computed by `post-review` from the block (§9.3).

## 4. Deployment

### 4.1 Creating one

```
cra init --company <git url | path> --workspace <agent-link workspace> --dir ~/reviews/acme
```

writes the deployment directory:

```
~/reviews/acme/
  compose.yaml          generated from docker/compose.template.yaml
  config.yaml           see 4.2
  .env                  GITHUB_TOKEN, hub, issue tracker and documentation index addresses
  .agent-link.json      { "workspace": "<workspace>" }
  CLAUDE.md             generated coordinator prompt
  .claude/agents/       specialist.md, merger.md (copied from framework)
  .claude/settings.json deny list (4.5)
  .mcp.json             MCP servers (issue tracker, documentation index) pointing at the host gateway
  company/              clone of the company repo (or symlink when a path was given)
  runs/                 bind-mounted; results land here, readable by host agents
  clones/               bind-mounted; long-lived clones of polled repos
```

`cra update` re-renders the generated files from a newer framework without touching
`config.yaml`, `runs/` or `company/`.

**Compose.** One service, `reviewer`. The deployment directory itself (`CLAUDE.md`,
`.claude/`, `.mcp.json`, `.agent-link.json`, `config.yaml`, `company/`, `runs/`, `clones/`) is
bind-mounted and is the coordinator's working directory; the whole `/home/reviewer` is a named
volume (§4.3a);
each `local_roots` entry is a read-only bind mount at the same path as on the host, so paths
in requests need no translation. `docker compose exec reviewer tmux attach` opens the window.

### 4.2 `config.yaml`

```yaml
framework: /opt/code-review-ai          # inside the image; informational
company:
  repo: git@github.com:acme/review-guidelines.git   # or a local path
  ref: main
github:
  identity: acme-review-bot             # the account the PAT belongs to
  repos:                                # polled; PRs requesting review from the bot
    - acme/widgets
    - acme/billing-api
  poll_interval_minutes: 10
local_roots:                            # host dirs mounted read-only for local: targets
  - /home/you/dev
agent_link:
  name: code-reviewer                   # name within the workspace
  notify: human                         # peer that receives results of polled runs
limits:
  max_concurrent_runs: 2
  max_specialists_per_run: 7
  max_tokens_per_run: 4000000
models:
  specialist: { model: claude-opus-5-5, effort: high }
  merger:     { model: claude-sonnet-5-5, effort: medium }
```

### 4.3 Image

Debian base. The entrypoint starts as root only to install the firewall rules, then drops to
the non-root user `reviewer` with `gosu` before starting tmux and Claude
(`--dangerously-skip-permissions` refuses root). Installed:
Claude Code, the agent-link plugin, `gh`, `git`, `tmux`, `jq`, `yq`, Node 24, Go, Python 3 with
`pip` and `uv`, a JDK with Maven and Gradle, and the framework checked out at
`/opt/code-review-ai`. Toolchains exist so specialists can build and run tests to verify a
finding; nothing in the image assumes a particular stack beyond those four languages.

### 4.3a Claude Code updates and window lifecycle

Claude Code updates itself and an old version cannot be assumed to keep working, so the image
must not pin the binary. Rules:

- Claude Code is installed with the native installer into the `reviewer` user's home
  (`~/.local/bin` and `~/.claude`), and the **whole home** `/home/reviewer` is a named volume,
  so both the binary's self-updates and the login survive container restarts. The image only
  guarantees that some version is present on first boot.
- The entrypoint runs `claude update` before starting the window, every start.
- The window runs under a **supervisor loop** in tmux: when `claude` exits, the loop runs
  `claude update` and starts it again with `--continue`, which restores the conversation and
  its scheduled `/poll` job; `/boot` re-arms the job anyway if it is missing (scheduled jobs
  are session-scoped and expire after seven days). The coordinator's boot instructions (§6.3) make a
  restart cheap: reclaim the agent-link name, re-arm the cron, resume runs from disk.
- Claude Code offers no way to check for an update without installing it, so `cra check-update`
  runs `claude update` itself: it installs the new binary on disk while the running session
  keeps the old one, and reports whether anything changed. The coordinator calls it on each
  polling tick when no run is in `reviewing`/`merging`/`delivering`; when an update was
  installed, it finishes its tick and runs `cra restart-window`,
  which sends `/exit` to the coordinator's own tmux pane; the supervisor then restarts it on
  the new version. A run in flight is never interrupted for an update; the check repeats on
  the next tick.
- `cra update` runs on the host and restarts the window the same way through
  `docker compose exec reviewer cra restart-window`; `cra restart-window` itself always runs
  inside the container, where tmux is.

### 4.4 Networking and egress

The container runs on a bridge network with the Docker host gateway mapped
(`host.docker.internal`). The agent-link hub, an issue-tracker MCP server and a documentation index on the host
must listen on the Docker bridge address as well as loopback; `cra init` prints the exact
settings. Host networking is rejected because the egress firewall inside the container would
then edit the host's rules.

The entrypoint installs an iptables allowlist (needs `NET_ADMIN` at start): DNS,
`api.anthropic.com`, `github.com`, `api.github.com`, `objects.githubusercontent.com`,
`codeload.github.com`, package registries needed for builds (npm, PyPI, Go proxy, Maven
Central), and the host gateway on the hub, issue tracker and documentation index ports. Everything else is
dropped. The list is a file in the deployment so a company can extend it.

### 4.5 Permissions inside the container

Claude runs with permission prompts off. `.claude/settings.json` keeps a short deny list of
things no reviewer needs and that the PAT would otherwise allow: `git push`, every `gh pr`
write subcommand (`review`, `comment`, `edit`, `ready`, `merge`, `close`, `reopen`, `lock`),
`gh repo *`, `gh api` with a method other than GET, and `rm -rf` outside `runs/`. The only
GitHub write path is the `post-review` script, invoked by its own name, which the `gh pr
review` deny prefix does not match. The deny list is defence in depth; the real limits are the
token scopes (§4.6) and the read-only mounts. MCP servers (issue tracker, documentation index) are declared in
the deployment's `.mcp.json`, pointing at the host gateway.

### 4.6 Identities

- **GitHub**: a dedicated bot account per company with a fine-grained PAT restricted to the
  polled repos: `contents: read`, `pull-requests: write`, `metadata: read`. People request
  review from the bot; reviews post as the bot. The PAT lives in `.env` only.
- **Claude**: the operator runs `claude` once inside the container and logs in; the Claude
  home volume (§4.3a) keeps the refreshing token across restarts.
- **agent-link**: the coordinator registers as `agent_link.name` in the deployment's workspace.
  On restart the window reclaims the same name and its conversations (agent-link reclaims by
  name within a workspace).

## 5. Guideline model and the resolver

### 5.1 Roots and templates

> Amended after the first build day: the original design walked four layers in a fixed step
> order with `append`/`replace` modes. The project owner's review called that implicit and over-built; it was
> replaced by the template model below (task "Replace the layer-walk composer").

Each specialist prompt is built from a **prompt template** by expanding include lines. A
template is markdown; a line that is exactly `${root}/relative/path.md` is replaced by that
file, whose own include lines are expanded in turn. Four roots:

| Root | Location | Contents |
|---|---|---|
| `${framework}` | this repo | `prompts/specialist.md` (default template), identities, common policy, per-type guidelines, language and kind amendments |
| `${company}` | `company/` in the deployment, from `config.company.repo` | `defaults.yaml`, `projects/`, and whatever templates and guidelines the company writes |
| `${project}` | `company/projects/<name>/` | `manifest.yaml` plus project guideline files |
| `${repo}` | `.code-review/` inside the reviewed repo | `manifest.yaml` plus repository guideline files |

Framework directory shape:

```
prompts/specialist.md            default template
prompts/light.md                 identity + common policy + general checklist only
prompts/hexagonal-service.md     default + the hexagonal-service and persistence packs
prompts/standards-driven.md      default + the standards-driven pack
prompts/open-source.md           default + the open-source-release and quality-gates packs
prompts/full.md                  default + every pack
agents/
  coordinator.md                 coordinator identity (generated into CLAUDE.md)
  specialist.md  merger.md       subagent definitions
  types/<type>.md                specialist identity per review type
guidelines/
  common/*.md                    severity rubric, triage, re-review discipline, verification
                                 rule, output discipline, finding format
  types/<type>/general.md
  types/<type>/lang/<lang>.md    go, python, ts, java
  types/<type>/kind/<kind>.md    service, library, tool, website, contracts, spec
  packs/<pack>/<type>.md         opt-in sets a template includes: hexagonal-service,
                                 persistence, standards-driven, open-source-release, quality-gates
templates/company/               framework only: starter company repo with a sample project
```

The company repo has no required shape beyond the manifests: the default template looks for
company files at the same relative paths as the framework's, so a company that writes no
template of its own adds material by creating those files.

Review types: `security`, `testing`, `coding-practices`, `code-structure`, `architecture`,
`system-design`, `documentation` run when no manifest declares types; `spec-compliance` (did
the change build what was asked, nothing more, each requirement shown met) and `performance`
(what a path costs and what was measured) run only when a manifest lists them. Kinds:
`service`, `library`, `tool`, `website`, `contracts` (a shared wire-contract module consumed
by independently deployed services) and `spec` (a documents-only specification repository).

A **pack** is a directory `guidelines/packs/<pack>/<type>.md` that no default template
includes; a template opts in with `${framework}/guidelines/packs/<pack>/${type}.md?` (and the
company mirror). Packs hold rules that depend on a stack or a process choice rather than on the
kind: ports-and-adapters layering, database ownership, implementing published standards,
publishing to a public repository, tool-enforced quality gates.

### 5.2 Template language and file rules

- `${framework|company|project|repo}/path` alone on a line includes that file; a missing file
  is an error unless the line ends in `?`. `*` in the last path segment includes every match in
  name order and is never an error. `${task}` alone on a line is the task block (§5.4 item 8).
- `${type}`, `${kind}` and `${languages}` are substituted anywhere; a line containing `${lang}`
  is repeated once per language of the run.
- Included files may include further files (depth 8, cycles are errors), so a repository file
  can reference `${company}/python-style.md` and a company file can reuse another.
- An include can only reach files under its own root (symlinks resolved). A template may come
  from `${framework}`, `${company}` or `${project}`, never from `${repo}`: the reviewed repo may
  add to a prompt but cannot decide what the prompt is (§12). For a `pr` target `.code-review/`
  is read from the **merge-base with the base branch**, never from the PR head.
- Each included file is preceded by a provenance line `*${root}/path*`. After expansion,
  headings with nothing under them are dropped.
- Frontmatter: `applies_to: [pr, audit, local]` keeps a file out of other target kinds. The old
  `mode:` key is ignored.
- Every include considered, used or not, with its reason and content hash, goes to
  `resolution.json`.

### 5.3 Manifests

`projects/<name>/manifest.yaml` (company root):

```yaml
repo: acme/widgets                 # GitHub name, or a path prefix for local targets
kind: service                      # service | library | tool | website | contracts | spec
languages: [go, ts]
types:                             # which specialists run by default
  security:  { required: true, model: claude-opus-5-5, effort: xhigh }
  testing:   { required: true }
  coding-practices: {}
  documentation: { model: claude-sonnet-5-5, effort: medium }
posting: auto                      # auto | comment-only | never
siblings: [acme/widgets-sdk]       # extra clones mounted read-only for cross-repo checks
prompt: ${company}/prompts/specialist.md   # template for every type that sets none; per-type
                                           # `prompt:` overrides it; default ${framework}/prompts/specialist.md
```

`.code-review/manifest.yaml` (repo root) has the same shape but may only **add** types and
languages. It cannot remove a type the company marked `required: true`, change `posting`, or
name a `prompt`. The resolver reports any ignored field in `plan.json`.

A repo with no project manifest gets the company defaults (`company/defaults.yaml`, same shape
minus `repo`) and, failing that, the framework defaults: all seven types, languages inferred
from file extensions in the diff or tree, kind `service`. The framework default is the seven
default types; `spec-compliance` and `performance` run only when a manifest names them.

Precedence between `defaults.yaml` and a project manifest: scalar fields (`kind`,
`languages`, `posting`, `siblings`) come from the project when it sets them. For `types`, a
project's list decides **membership** (a project may run fewer types than the company
default), but every type the company marks `required: true` in `defaults.yaml` is added back
and recorded in `plan.json` under `addedRequired`. Per-type `model`/`effort`/`prompt` set in
`defaults.yaml` are inherited by a project that lists the type without them. The framework's
seven-type default applies only when no company manifest declares any types.

### 5.3a Request resolution: `resolve-run`

Everything between a request and the per-type prompts is one deterministic command, so no
model decides what gets reviewed with which rules:

```
resolve-run --request <request.json> --config <config.yaml> --company <dir>
            --target-guidelines <dir or none> [--files <files.json>] --out <plan.json>
```

`--files` is only consulted when the chosen manifest names no languages; it is still passed
in the normal flow (§8) so the record is complete.

It finds the project (manifest `repo` equal to the target repo, or the longest `repo` path
prefix for a local target), falls back to `company/defaults.yaml` then framework defaults,
merges the target manifest under the add-only rule, infers languages from `files.json` when
the manifest names none, applies request `types` narrowing and the `required: true` add-back,
and writes `plan.json`: project name, kind, languages, the ordered list of types with model,
effort and template, posting policy and the effective `post` decision, sibling repos, and the
four root directories. The coordinator reads `plan.json` and calls `compose-prompt` once per type
with values copied from it. `resolve-run` lives beside `compose-prompt` in `src/` and shares
its tests.

A `post: true` request on a `comment-only` project posts a comment; on a `never` project it is
refused and goes to the human (§7.1). `post` controls whether; the policy controls how.

### 5.4 Composition

`compose-prompt --type T --kind K --lang L... [--template ${root}/path.md] --framework <dir>
[--company <dir>] [--project <dir>] [--repo <dir>] --task <task.json> --out <file>` names each
root explicitly; only the framework is required, and an absent root makes every include under
it absent. It expands the template (§5.2). The framework's `prompts/specialist.md` yields, in
order:

1. identity: `agents/types/T.md` from the framework, then the company's if present
2. common: `guidelines/common/*.md` from the framework, then the company's
3. `guidelines/types/T/general.md`, `kind/K.md`, `lang/<l>.md` per language, framework then
   company
4. project: `common.md`, then `T.md`
5. repo: `common.md`, then `T.md`
6. task block rendered from `task.json`: target kind, repo, PR number and URL or ref, paths in
   scope, diff and metadata paths, sibling paths, prior review path, requester context, the
   exact output path, and the frontmatter the findings file must begin with.

A company template may list anything else in any order.

It also writes `resolution.json`: the template, every include considered with the file that
included it, whether it was used, why not, and its content hash. `review.md` points at it, so
any review is traceable to the exact text each specialist saw.

The resolver is pure and offline: same inputs, same bytes. It is a TypeScript CLI on Node 24
with no build step, tested with `node --test` over fixture trees, plus snapshot tests of
composed prompts so that a guideline edit shows its effect in the diff.

### 5.5 Framework content in v1

- `common/`: ported from the old `review_root/internal/CLAUDE.md`, generalised: severity rubric,
  merge verdict, relation / fix cost / fix risk triage, re-review discipline, "do not assert
  what you could not verify", output discipline, the findings block format (§9.1). Company-
  specific material from the old file (leak rules, MCP server names, org names) is **not**
  ported; it belongs in a company overlay. The old file is a worked example for the starter
  template, with names replaced.
- `types/<type>/general.md` for all nine types (the two opt-in ones added 2026-10-12).
- `lang/<lang>.md` for Go, Python, TypeScript and Java where a type has language-specific
  content (coding-practices, testing, security, code-structure at minimum). Absent files are
  simply skipped.
- `kind/<kind>.md` wherever a kind changes what to look for; after the 2026-10-12 library
  pass most type × kind cells exist, including the `contracts` and `spec` kinds.
- `packs/<pack>/<type>.md` for the five opt-in packs, and the ready templates under
  `prompts/` that include them.
- `templates/company/`: a working starter with `defaults.yaml`, one sample project, example
  additions at the paths the default template looks for, and an example company template.

## 6. Requests and runs

### 6.1 Request

Both intakes produce `runs/<run-id>/request.json` for every request that starts a run. A
`status` request is answered from `runs/index.jsonl` and creates nothing.

Three different words are deliberately kept apart: a request has an **action**, a target has a
**kind**, and a project manifest has a **kind** (what the software is).

| action \ target kind | `pr` | `audit` | `local` |
|---|---|---|---|
| `review` | review the PR diff | audit the tree at `ref` (scoped by `paths`) | review the working-tree diff against `ref` |
| `rereview` | prior posted review + new commits | not applicable: an audit is always a fresh `review` | prior run + changed snapshot |
| `status` | no run; answers from the index | same | same |

`types` in a request may narrow the manifest's default set but a type the company marks
`required: true` is always added back, and the addition is noted in the acknowledgement.

```json
{
  "id": "2026-10-11T14-03-22Z-acme-widgets-123",
  "action": "review",               // review | rereview
  "target": {
    "kind": "pr",                   // pr | audit | local
    "repo": "acme/widgets",         // pr, audit
    "number": 123,                  // pr
    "ref": "main",                  // audit; base for local
    "path": "/home/you/dev/widgets",// local (host path as the requester sees it)
    "paths": ["internal/token"]     // optional scope, audit and local
  },
  "types": ["security", "testing"], // optional; else manifest defaults
  "post": true,                     // optional; else project posting policy; ignored for audit/local
  "context": "free text from the requester",
  "source": { "intake": "agent-link", "conversation_id": "cv_…", "from": "builder" }
}
```

Over agent-link the request is markdown with a fenced YAML block carrying the same fields,
followed by free text, so both humans and agents can write it:

````markdown
```yaml
action: review                  # review | rereview | status
target: acme/widgets#123        # pr: owner/repo#N · audit: owner/repo@ref [paths: ...] · local: local:/host/path
types: [security, testing]
post: false
```
This PR replaces the token cache; please focus on invalidation.
````

### 6.2 Run lifecycle

```
queued → preparing → reviewing → merging → delivering → done
                 ╲        ╲          ╲          ╲
                  └────────┴──────────┴──────────┴──► failed (reason in run.json)
                       blocked (waiting on a human answer, §7.1)
```

`runs/<id>/run.json` holds status, timestamps, the target identity (head SHA, or snapshot
identity for local), selected types, token usage per subagent, and the delivery record
(`posted_sha`, review id, agent-link message ids). `runs/index.jsonl` appends one line per
state change; status queries and the TUI-less `cra status` read it.

Run directory:

```
runs/<id>/
  request.json  run.json  plan.json  resolution.json
  target/        worktree, checkout or snapshot (local)        [removed after done, kept on failed]
  meta/          diff.patch, pr.json (comments, reviews), files.json, target-guidelines/
  prompts/<type>.md
  findings/<type>.md
  review.md      posted.md
  log/           coordinator.log, <type>.jsonl (subagent transcripts)
```

### 6.3 Concurrency and resumption

The coordinator processes the queue up to `limits.max_concurrent_runs`, dispatching a run's
specialists in parallel with the Agent tool. On startup (fresh container, supervisor restart after
a Claude Code update, `/clear`, `/resume`), the generated `CLAUDE.md` instructs it to register
on agent-link, re-arm the polling cron, re-queue runs left in `preparing` or `reviewing`, and
resume runs in `merging` or `delivering` from their findings on disk. Nothing the coordinator
needs lives only in its conversation; every state transition is on disk first.

## 7. Intakes

### 7.1 agent-link

The coordinator registers once per session with a description along the lines of: *reviews
pull requests, audits repositories or paths, reviews local working trees without publishing,
re-reviews after a push, reports run status, explains a finding*. It handles messages as
follows:

- A request with `expectation: reply` gets one acknowledgement (run id, selected types,
  whether it will post) and one final message with the verdict, counts by severity, the
  host-side path of `review.md`, and `final: true`.
- `expectation: updates` adds a message on each state change.
- `action: status` answers from `runs/index.jsonl` without starting a run.
- Anything the coordinator cannot resolve on its own — an unknown repo, a local path outside
  `local_roots`, a request to post on a project whose policy says `never`, a review type that
  does not exist — goes to the human relay in the workspace with `expectation: reply`, and the
  run sits in `blocked`. If no human peer is online the run fails with that reason and the
  requester is told.
- A polled run has no requester; its completion goes to `agent_link.notify` with
  `expectation: none`.
- The coordinator may ask the requesting agent a clarifying question in the same conversation
  before preparing the run, but never more than once per run.

Peers can also ask about a finding (*why is #3 Major?*). The coordinator answers from the
findings file and the resolution record; it does not rerun specialists for that.

### 7.2 GitHub polling

The coordinator owns a Claude Code in-session scheduled task (the `CronCreate` mechanism) that
fires every `github.poll_interval_minutes` and runs `discover`; the coordinator itself queues
what `discover` prints. There is no system cron and nothing outside the window writes to
`runs/`. `discover` has two candidate sources, because GitHub clears a review request the
moment the bot submits a review, so a reviewed PR disappears from the request listing:

1. **Requested**: for each configured repo, open, non-draft PRs where the bot is a requested
   reviewer (`user-review-requested:@me` as the bot), excluding bot authors (dependabot and
   similar). A PR with no run on record becomes `action: review`. A PR whose latest `done` run
   has a `posted_sha` is a **re-request** (GitHub cleared the request when the bot posted, so
   its presence means someone asked again) and becomes `action: rereview` even if its head SHA
   is unchanged: the author may have answered in the thread without pushing, and the re-review
   reads the thread. A PR whose latest run has no `posted_sha` (a `posting: never` project, or
   a run that did not reach delivery) is never a re-request; it follows the tracked rule.
2. **Tracked**: every PR that has any run on record and is still open. If its head SHA differs
   from the SHA on record it becomes `action: rereview`.
3. **The SHA on record** is the target identity in the latest `run.json` for that `(repo,
   number)`, whatever its status. So a PR whose run is `queued`, `preparing`, `reviewing`,
   `merging`, `delivering` or `blocked` is skipped; a push during an in-flight or blocked run
   is picked up on the first tick after that run finishes or fails. A `failed` run is retried
   once on the next tick as a **new run** with `attempts: 2` and `retry_of` pointing at the
   failed one, then left alone until a push or an explicit request. A project with
   `posting: never` has no `posted_sha`; its prior `review.md` is the prior review and the same
   identity rule applies.
4. A tracked PR that is now merged or closed is retired: its entry is marked `retired` in
   `runs/index.jsonl`, its fetched ref and any leftover worktree under `clones/<repo>/` are
   pruned. Losing the review request alone never retires a PR.

State lives in `runs/` only; there is no database.

## 8. Target preparation

`prep-target` is a bash script with one subcommand per target kind plus `siblings`. It never
writes outside the run directory and the clones it owns. The order within a run is fixed:

```
prep-target <pr|audit|local>  →  resolve-run  →  prep-target siblings  →  compose-prompt ×N
   (target/, meta/files.json,      (plan.json)      (clones from plan.json,
    meta/target-guidelines/)                          paths into task.json)
```

- **pr** — ensure the long-lived clone under `clones/`, fetch the PR ref, create a worktree at
  the head SHA under `runs/<id>/target/`, write `meta/diff.patch` (against the merge-base with
  the base branch), `meta/pr.json` (title, body, comments, reviews, requested reviewers),
  `meta/files.json`, and extract `.code-review/` **at the merge-base** into
  `meta/target-guidelines/` (empty directory when absent).
- **audit** — ensure the clone, check out `ref` into `runs/<id>/target/`, write `files.json`
  limited to `paths` when given, copy `target/.code-review/` to `meta/target-guidelines/`. No
  diff.
- **siblings** — given `plan.json`, ensure a read-only clone of each sibling repo under
  `clones/` and print their paths for the task block. Runs after `resolve-run` because only
  the resolved project knows its siblings.
- **local** — the host path is mapped to its read-only mount. Snapshot into
  `runs/<id>/target/`: `git clone` of HEAD from the mount, then apply `git diff HEAD --binary`
  taken from the mount, then copy untracked, non-ignored files. Record HEAD plus a hash of the
  applied patch as the target identity. Write `meta/diff.patch` against `ref` (default: the
  merge-base with the repo's default branch). A `rereview` of an unchanged identity returns
  the existing run instead of reviewing again. `target/.code-review/` is copied to
  `meta/target-guidelines/`. The mount is never written.

## 9. Review output

### 9.1 Findings file

Each specialist writes `findings/<type>.md`: the frontmatter dictated by the task block, then a
fenced `findings` YAML block, then prose. The YAML block is what the merger reads:

```yaml
- id: security-1
  severity: major             # critical | major | minor | nit
  relation: caused-by-change  # caused-by-change | adjacent | pre-existing
  fix_cost: trivial           # trivial | moderate | involved
  fix_risk: contained         # contained | rippling
  title: JWKS cache never invalidates on key rotation
  location: internal/jwks/cache.go:88
  evidence: "ttl is read once at construction; rotation path never calls Reset()"
  verified: true              # false when the specialist could not run the check
  recommendation: blocks      # blocks | fix-now | optional | follow-up
```

Prose after the block may elaborate, but a finding not in the block does not exist.

### 9.2 Merged review

`review.md` begins with frontmatter (run id, target identity, types run, resolution path, token
totals), then a fenced `findings` YAML block in the §9.1 shape with two extra fields per entry
(`sources: [security, testing]` and `merged_from: [security-1, testing-4]`), then the verdict
line, the triage table, then findings grouped by severity as prose. The block is the
authoritative content; prose that mentions a finding absent from the block is a merger error
and `post-review` refuses the run. For a `rereview`, the block carries a `withdrawn` list
(prior finding ids and a reason) and the first prose section lists them, per the common
guidelines. Audits replace the verdict with a summary by type and end with a **follow-up
tasks** list (title, severity, location, one-line scope) that a human or another agent can
file wherever work is tracked.

### 9.3 Verdict rule

Computed by `post-review` from the merged block, never taken from prose: any entry with
severity critical or major **and** `recommendation: blocks` → `request-changes`; otherwise
`approve`. A project with `posting: comment-only` posts `comment`. If the merger's verdict line
disagrees with the computed verdict, the computed one is posted and the disagreement is
logged in `run.json`. Audits and local targets have no verdict to post.

## 10. Delivery

1. `review.md` is on disk under the bind-mounted `runs/`, so host-side agents read it by path.
2. The agent-link reply or notification is sent (§7.1).
3. For a PR with posting allowed, `post-review` adapts `review.md` into `posted.md` (drops
   frontmatter, keeps severity-prefixed findings with `file:line`), submits it with
   `gh pr review --<verdict> --body-file`, and records `posted_sha`. The script is the only
   thing that calls `gh` for a write, and it refuses any run whose target is not `pr`.

## 11. Models, cost, caps

- Specialists default to `models.specialist`; a manifest overrides per type.
- The merger defaults to `models.merger`.
- Each subagent's reported usage is written to `run.json` when it returns. Usage is only known
  then, so `limits.max_tokens_per_run` is checked between phases: after the specialists return
  and before merging, and after merging before delivering. A run over the cap is marked
  `failed` with the per-type breakdown; nothing is killed mid-flight.
- `limits.max_specialists_per_run` caps fan-out; extra types are dropped lowest-priority first
  (order: security, testing, coding-practices, code-structure, architecture, system-design,
  documentation) and the drop is recorded.

## 12. Security considerations

- Reviewed content is untrusted. A PR can carry instructions aimed at the specialists. The
  limits on damage are: the PAT cannot push code, open PRs, or touch anything but reviews on the
  configured repos; egress goes only to the allowlist; local mounts are read-only; the merger
  cannot add findings; and the post script applies a fixed verdict rule. A poisoned review is
  possible and is accepted as the residual risk of autonomous posting; the common guidelines
  tell specialists to flag instructions found in reviewed content as a finding, not follow them.
- Secrets: the PAT and nothing else in `.env`; the Claude token in its volume; neither is
  readable from the reviewed tree. Specialists are told never to print token material.
- The company repo is trusted as code: its guidelines are instructions.

### 13.1 Implementation order

The pieces depend on each other in one direction, so the plan is phased:

1. Resolver and framework content (common policy, type identities, general guidelines), since
   every later piece depends on the prompt and findings shape.
2. Scripts: `prep-target`, `discover`, `post-review`, with their tests.
3. Coordinator, specialist and merger prompts; the request protocol; run lifecycle.
4. Image, compose template, firewall, `cra init/update/status/check-update`; smoke test.
5. Language and kind amendments and the company starter template, as a content stream that
   can run alongside 2 to 4 once 1 has fixed the shape.

Each phase gets its own implementation plan; this spec is the shared contract between them.

## 14. Testing

- **Resolver**: unit tests over fixture trees covering template expansion order, optional and
  required includes, globs, per-language expansion, nested includes, root confinement
  (including symlinks), cycles, `applies_to` and empty-heading removal; snapshot tests of
  composed prompts for each type × a Go service and a TS library.
- **Resolution**: `resolve-run` unit tests for project lookup, defaults fallback, target
  add-only merge, language inference, request narrowing with required add-back, and the
  `post` × policy matrix.
- **`prep-target`**: bats with fixture repos for all three kinds, including the local snapshot
  with uncommitted and untracked changes and the merge-base `.code-review/` rule.
- **`discover` and `post-review`**: `node --test` with a stubbed `gh` on `PATH` and fixture
  `runs/` trees: both candidate sources, re-request only with a `posted_sha` (a
  `posting: never` project must not loop), in-flight and blocked skip, failed retry-once as a
  new run, retire;
  verdict mapping from the merged block, prose-block mismatch refusal, refusal of non-PR runs.
- **Compose smoke test**: build the image, start a scratch hub on the host, bring up a
  deployment against a fixture company repo, send one request over agent-link, assert a
  `review.md` with the expected frontmatter appears in `runs/`. Run on demand, not in unit CI.
- **Review quality**: out of v1. A small set of PRs with known findings will later serve as an
  eval for the guidelines.

## 15. Out of scope for v1

- A TUI or web UI; `cra status` and the files are the interface.
- Filing audit follow-ups into any tracker automatically.
- GitHub App identity, GitLab or other forges.
- Multiple coordinator peers per deployment, or a shared queue across machines.
- Resuming a specialist session interactively (the old TODO); transcripts are kept in `log/`
  so it can be added later.
